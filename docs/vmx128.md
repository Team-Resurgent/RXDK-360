# Spike 3 — is VMX128 fatal?

VMX128 is Xenon's extension of AltiVec from 32 vector registers to 128, with extra
instructions. LLVM has AltiVec and VSX; it has no VMX128. This was flagged as the item
most likely to sink the project. **It is not fatal.** Three separate questions were
conflated; they have different answers.

## 1. Does the *API* require VMX128? No.

```
$ grep -rhoE '__v[a-z0-9_]*128' include/xbox/
(no matches)
```

The headers declare **zero** `__v*128` intrinsics. `vectorintrinsics.h` declares 160
intrinsics under plain names (`__lvx`, `__vaddfp`, `__vor`, ...). VMX128 is the MS
compiler's *encoding choice* when it allocates a register above 31 — visible in our
probe as `vor128 vr127,vr2,vr2` and `stvx128 vr127,r1,r12`. For registers 0-31 the
same operations encode as ordinary AltiVec.

The shipped libraries' own compiled code contains real VMX128 instructions, and that is
fine — we link that code, we do not regenerate it.

## 2. Does the vector *ABI* need registers LLVM cannot name? No — but it is off by one.

Probe (`spike/vmx/vec2.c`), `def_mixv(int a, V b, float c, V d, int e)`:

| | a | b | c | d | e |
|---|---|---|---|---|---|
| MS | r3 | **vr1** | fr1 | **vr2** | r5 |
| zig / SysV | r3 | **v2** | f1 | **v3** | r5 |

Vector arguments live in `vr1..vr13` under MS and `v2..v13` under SysV — **all inside
the 32 registers LLVM can address.** With 14 vector arguments MS used `vr1-vr13` plus
`vr116-vr127` as callee-saved scratch; the high registers are internal to MS code,
saved and restored by it, and our code never touches them.

Note also that vector arguments do **not** consume a positional GPR slot the way
floating-point arguments do (`e` landed in r5, not r7).

So this is one more systematic divergence for the calling-convention work, not a
capability gap.

## 3. Does *our* code need to generate VMX128 instructions? Only for the math library.

XNAMath (`xnamath.h` + `xnamath*.inl`) is implemented as inline bodies, so a title
compiles them itself. Those bodies use 71 distinct intrinsics. Most are ordinary
AltiVec, but these are Xenon-only *instructions*, not merely encodings:

| intrinsic | uses | AltiVec replacement |
|---|---|---|
| `__vmsum4fp` / `__vmsum3fp` | 891 / 118 | `vmulfp` + horizontal add via `vsldoi`+`vaddfp` (~4 insns) |
| `__lvlx` / `__lvrx` | 584 / 232 | classic `lvsl` + `lvx` + `vperm` unaligned idiom |
| `__vrlimi` | 473 | `vsldoi`/`vperm` + `vsel` |
| `__vmaddcfp` | 361 | `vmaddfp` variant |
| `__vpermwi` | 324 | `vperm` with a constant permute vector |
| `__vupkd3d` / `__vpkd3d` | 214 / 75 | multi-instruction sequence per D3D format |

~3270 uses in total. Every one is expressible as a short AltiVec sequence — correct,
but slower. A 1-instruction dot product becoming ~4 is a real cost in math-heavy code.

## Verdict

VMX128 costs a **reimplemented XNAMath on AltiVec** plus reduced vector register
pressure (32 instead of 128). It does not block linking, does not block the ABI, and
does not block correctness. It is a performance tax and a bounded piece of work, not a
wall.

Adding VMX128 to LLVM's PPC backend remains available later as an optimisation, and
would be independently useful.

## Still unchecked

  way that breaks callbacks from MS code into ours.
